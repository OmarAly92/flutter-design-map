# flutter-design-map-skills

Produce a visual map of a Flutter app's navigation: every route as a card with a screenshot, runtime state variants (bottom sheets, dialogs, modals), and navigation edges — packed into an expo-map-compatible `.appmap` bundle.

**Arguments:** optional path to the Flutter project (default: cwd). `--static` = parse + pack only (no simulator). `--prepare` = parse + write deep-link flow stubs / explore plan, stop before live capture.

**Working directory:** all outputs go to `<project>/.flutter-map/` — `graph.json`, `explore-plan.json`, `capture-status.json`, `screens/*.png`, `flows/*.yaml` + `flows/*.meta.json`, `*.appmap`. Suggest adding `.flutter-map/` to `.gitignore`.

## Resolve `$PARSER` first

The pack/parse CLIs are a Dart package shipped alongside this skill at
`<repo>/packages/flutter_map_parser`. Before Phase 1, set `$PARSER` to the first
of these that exists — substitute the real directory this `SKILL.md` was loaded
from for `<skill-dir>`:

```bash
SKILL_DIR="$(cd '<skill-dir>' && pwd -P)"   # pwd -P resolves a symlinked skill dir
PARSER=""
for candidate in \
  "${CLAUDE_PLUGIN_ROOT:-/nonexistent}/packages/flutter_map_parser" \
  "${PLUGIN_ROOT:-/nonexistent}/packages/flutter_map_parser" \
  "$SKILL_DIR/../../packages/flutter_map_parser"
do
  [ -d "$candidate" ] && PARSER="$(cd "$candidate" && pwd -P)" && break
done
echo "${PARSER:-not found}"
```

The third candidate is the normal case: `<repo>/skills/flutter-design-map-skills` → up two
levels → `<repo>`. It covers `install.sh`'s symlink too, because `pwd -P`
resolves back into the real checkout.

If nothing is found, clone the repo and use `<clone>/packages/flutter_map_parser`:

```bash
git clone https://github.com/OmarAly92/flutter-design-map
```

**Then fetch dependencies and verify — both, in this order, always.** A plugin
install ships the parser source without its `.dart_tool/`, and
`dart run <absolute-path>` does *not* resolve dependencies on its own; it fails
with `Couldn't resolve the package 'args'`. `dart pub get` is idempotent and
fast when already resolved, so just run it every time:

```bash
(cd "$PARSER" && dart pub get)
```

```bash
dart run $PARSER/bin/parse_routes.dart --help
```

If `dart pub get` fails because `$PARSER` is not writable, copy the package to a
writable location and point `$PARSER` there. Do not continue past a failing
`--help`: every phase below depends on these CLIs.

Every command below assumes `$PARSER` is set:

```bash
dart run $PARSER/bin/parse_routes.dart <project>
dart run $PARSER/bin/prepare_explore.dart <project>
dart run $PARSER/bin/pack_map.dart <project>
# or: dart run $PARSER/bin/flutter_map.dart <project>
```

## Flow recording (Phases 4–5)

Record interactions as **argent** flows: `<name>.yaml` + `<name>.meta.json` under `.flutter-map/flows/`. Replay: `npx @swmansion/argent flow run .flutter-map/flows/<name>.yaml`. Schema: `docs/appmap-format.md`.

Rules:
- Prefer argent MCP recording when connected; otherwise write YAML with normalized 0–1 coordinates.
- Sidecar `steps` keyed by 0-based YAML index. Navigating taps need `"screen": "<route id>"`. Screenshots are sidecar `capture` fields — never YAML steps.
- Record each successful action when it happens; do not reconstruct flows afterward. Prefer durable accessibility/text selectors over coordinates whenever Argent exposes them.
- Attach `capture` to the YAML step after which the screenshot was taken. Every coordinate tap/swipe also needs a human-readable `target` or `note`.
- Mechanical deep-link flows are generated by `prepare_explore` — keep and update them after live captures.
- Never record credentials; use `{{secret:NAME}}` if input is unavoidable.
- Never tap destructive controls (delete, purchase, sign out, submit).

## Phase 1 — static parse

```bash
dart run $PARSER/bin/parse_routes.dart <project>
```

Report `graph.json` summary: mode (`go_router` / `go_router_builder` / `auto_route` / `navigator` / `navigator_2`), route count, edges (flag unresolved), state hints, params, scheme. If mode is unknown, stop.

Edges resolve literal paths, path helpers/consts (`AppPaths.foo`, `Routes.settings.root`, getters like `Routes.newPersonPath`), and interpolated literals (`'${Routes.tutorials}/$id'`). AutoRoute also covers `context.router.push`, `context.pushRoute`, `AutoRouter.of(context).push/replaceAll`, router fields like `_appRouter?.push`, and `Navigator.push` of known `*Screen`/`*Page` widgets. Navigator mode covers `pushNamed` / `Navigator.pushNamed` / `Navigator.of(context).pushNamed`, the replacing variants (`pushReplacementNamed`, `pushNamedAndRemoveUntil`), and the `context.pushNamed(...)` extensions projects wrap them in. `onGenerateRoute` resolves as an inline closure, a top-level function, or a tear-off of a static method on a class in another file (`onGenerateRoute: AppRouter.generateRoute`); its `switch` cases resolve against project-wide constants, so `case RoutesStrings.loginScreen:` works when the constants live in their own file. `fullscreenDialog: true` is recorded as a `modal` presentation. Navigator 2 mode derives routes from `RouterDelegate` `pages:` stacks (plus `ValueKey` / `RouteInformationParser` path hints) and emits root→page stack edges.

`from` attribution walks widget composition, so a nav call in `.../ui/widgets/settings_body.dart` is attributed to the screen that builds it. Files reachable from more than one route (shared core widgets) are left unattributed rather than guessed, so some real edges will be missing — prefer recorded flows over the static graph when a screen is reached from a shared widget.

If `--static`, jump to Phase 6 (pack with missing captures).

## Phase 2 — prepare explore plan

```bash
dart run $PARSER/bin/prepare_explore.dart <project>
```

This writes:
- `.flutter-map/explore-plan.json` — per-route deep links, sample params, `simctl`/`adb` commands, screenshot paths
- `.flutter-map/flows/deeplink-<slug>.yaml` + `.meta.json` — deterministic open-url flows
- `.flutter-map/capture-status.json` — all routes start as `missing`
- `.flutter-map/screens/` directory

Review sample params: prefer values from resolved edge targets (e.g. `/details/42`), then fixture/seed data, else `1`. Edit `explore-plan.json` if needed before sweeping.
Auth-gated routes and redirects are expected findings: plan how to distinguish a real auth wall from a broken deep link before capture begins.

If `--prepare`, stop here and report the plan.

## Phase 3 — boot the Flutter app

1. Prefer an already-running app on a booted simulator/emulator.
2. iOS: `xcrun simctl list devices booted`. Android: `adb devices`.
3. Run the app (`flutter run -d <device>` or attach to an existing debug session). Note the bundle id / application id.
4. **Verify deep linking** using the scheme from `graph.json` / `explore-plan.json`:
   - iOS: `xcrun simctl openurl booted "<scheme>://"`
   - Android: `adb shell am start -a android.intent.action.VIEW -d "<scheme>://"`
5. Confirm the app rendered (screenshot). If deep links fail, fix Android intent-filters / iOS URL types, or continue with in-app navigation only and mark `needsNavigation` later.
6. On iOS, the first deep link after an install shows a system dialog (`Open in "<app>"?`). It blocks until confirmed and does not reappear for later links, so tap **Open** here in Phase 3 rather than letting it stall route 1 of the Phase 4 sweep. Android does not prompt.

Deep links use `<scheme>:///<path>` (three slashes). With `<scheme>://<path>` the first segment parses as the URI host and the path is empty, so the route never resolves — Android drops it outright.

## Phase 4 — route sweep

For each route in `explore-plan.json`:

1. Open `deepLink` (or the platform command in the plan).
2. Wait ~1.5s (3–4s for network-heavy screens).
3. Capture using the exact `slug`:
   - iOS: `xcrun simctl io booted screenshot <project>/.flutter-map/screens/<slug>.png`
   - Android: `adb exec-out screencap -p > <project>/.flutter-map/screens/<slug>.png`
4. Update the matching `flows/deeplink-<slug>.meta.json` `device` field once known.
5. Sanity-check periodically. Keep bad captures but note them for Phase 4b.

### Phase 4b — review and recover

Render and open a draft contact map before classifying captures:

```bash
dart run $PARSER/bin/render_map.dart <project>
```

Inspect every card. Loading skeletons get a longer retry; fake IDs should be replaced with real fixture/API values; redirects are classified by what actually rendered. After any red error screen or sticky error boundary, restart the app and re-capture the remaining tail so one failure does not silently poison later screenshots.

Write verdicts to `.flutter-map/capture-status.json`:

```json
{ "<routeId>": { "status": "ok", "needsNavigation": false, "note": null } }
```

Statuses: `ok` · `empty-state` · `not-found` · `error-boundary` · `loading` · `auth-wall` · `missing`.

Flutter-specific notes:
- Red error screens / yellow-black stripes → `error-boundary`; relaunch the app before continuing (`flutter` hot restart, or terminate + relaunch) — error UI can poison later captures.
- GoRouter redirects (auth) → capture what rendered; set `auth-wall` or note the redirect target.
- Routes that only work via typed `context.router.push` / shell tabs may need `needsNavigation: true` if bare deep links land on the wrong stack.

## Phase 5 — runtime states

For each route with non-empty `stateHints`:

- **bottom-sheet** — find the trigger in `file`, tap it, capture `screens/<slug>--sheet.png` (or `--sheet-<snap>` if snap points exist).
- **dialog** — trigger, capture `screens/<slug>--dialog.png`, dismiss.
- **modal** / **router-modal** — capture variant or treat as own route if already in the graph.

Coverage line required: `state hints: N · captured M · skipped K (why)`.
Treat the hint list as a required work queue. Re-open the base route between states, capture every parsed sheet snap point, and explicitly record why any hint could not be triggered safely.

### Phase 5b — navigation flows

For every reachable route, record `flows/nav-<slug>.yaml` + sidecar from app root. Walk the app depth-first and reuse verified prefixes, while keeping each flow self-contained. Every navigating tap/swipe must include the destination `screen` after visually confirming the landing.

When an action opens a drawer, menu, sheet, or dialog without changing routes, capture it once as `<source-slug>--<state>.png` and attach it to that action in every flow using it. Screens with no safe discoverable path should be marked `needsNavigation` with a concrete reason instead of inventing a flow.

## Phase 6 — pack and deliver

```bash
# optional downscale on macOS
for f in <project>/.flutter-map/screens/*.png; do sips -Z 800 "$f" >/dev/null; done

dart run $PARSER/bin/pack_map.dart <project>
dart run $PARSER/bin/render_map.dart <project> # self-contained .flutter-map/map.html
```

Deliver the `.appmap` zip. Open it in `apps/flutter_map_visualiser` (`flutter run -d chrome`) or the expo-map visualiser (drag-drop). Report: routes captured / total, state variants, skips, unresolved edges. Suggest gitignoring `.flutter-map/`.

## Replay

```bash
npx @swmansion/argent flow run <project>/.flutter-map/flows/<flow-name>.yaml
```

Fallback: execute YAML steps via `simctl`/`adb` + simulator MCP using sidecar `target` labels.

Legacy JSON flows can be migrated once with:

```bash
dart run $PARSER/bin/convert_flows.dart <project> --delete-v1
```

## Web fallback

When no simulator/emulator is available, run the app in Chrome, enumerate the same parsed paths, and capture each route at a fixed phone-sized viewport. Browser capture cannot validate native navigation stacks or system gestures, so report those limitations and do not claim navigation-flow coverage unless the interactions were actually replayed and verified.
